# Spec: Character Physical Description & Weapons/Gear

## Status
Implemented

## Summary
Extends [Main Story](main-story.md)'s character identity block: each player can write free-text about their character — a physical description, and separately their weapons/gear — each viewable and editable from the right panel, each capped at 500 characters. Unlike name/role/level (locked forever at creation), both are mutable at any time, like the avatar. Their purpose isn't just flavor — both are fed to Claude so it can factor appearance and equipment into NPC reactions and the scene, the same way [character-role-level.md](cyberpunk-red/character-role-level.md)'s Role already informs the DM without a player restating it every session. The two fields are identical in behavior (same component, same limit, same save mechanics) — Weapons & Gear was added as a direct extension of the Description field, added second, sitting directly beneath it.

## Requirements
- [x] In a Main Story conversation, a player can write, view, and edit a physical description of their own character, up to 500 characters
- [x] In a Main Story conversation, a player can write, view, and edit a Weapons & Gear list for their own character, up to 500 characters, directly beneath the description control
- [x] Neither field is shown by default — each is tucked behind its own small control in the right panel that reveals it on demand, distinct from the always-visible name/Role-Level/avatar
- [x] Saving is an explicit action (not autosave-on-blur/Enter, since these are multi-line fields where Enter should just add a newline)
- [x] The 500-character limit is enforced while typing (can't type past it) and is authoritative server-side regardless of what the client sends, for both fields
- [x] Each field is associated with that specific Main Story and that specific player, same as the avatar — persists and reappears whenever that user reopens that conversation
- [x] Both are absent for non-Main-Story conversations, same as the rest of the character-identity block
- [x] When Claude generates a DM reply in a Main Story conversation, it has access to each character's physical description and Weapons & Gear (whichever have been saved) so it can factor both into NPC reactions and the scene
- [x] Clicking a field's control opens a modal for viewing/editing that field, rather than expanding inline in the right panel — same modal shape (title, textarea, counter, Cancel/Save) for both fields, each opened independently
- [x] Description and Weapons & Gear's controls render as a row of small square icon buttons (icon only, no text inside the button) rather than text-label buttons; each button has a small text caption centered beneath it ("Description", "Gear" — Weapons & Gear's caption is shortened, its modal title stays "Weapons & Gear")
- [x] Description's button icon matches the UI handoff mockup (📝); Weapons & Gear's is 💼 — see Decisions for the lucide-react → emoji reversal

## Decisions
- **Mutable, not locked-at-creation.** The request says "view it, edit it, save it" with no mention of a creation step or permanence — matches the avatar's lifecycle (`avatar_images`), not the name/role/level's (locked forever). No creation-time prompt for it; it starts empty and is opt-in whenever a player gets to it.
- **Storage**: two new jsonb columns on `conversations` — `character_descriptions` and `character_gear`, each shaped `{ "<username>": "<text>" }` — same per-username mutable-map convention as `avatar_images`, kept as separate columns (not folded into one) so a component that only needs one field isn't forced to also fetch/parse the other.
- **Who can edit**: a player can only write their own fields, same self-directed model as the avatar — no editing the other player's, no admin override (there's no safety/consistency reason to need one here, unlike message locking).
- **500-character limit (reduced from an initial 1000)**: the user asked to lower Description's limit to 500 at the same time Weapons & Gear was added, and to give the new field the same limit — both fields now share one constant server-side (`MAX_TEXT_FIELD_LENGTH`).
- **Shared component**: since Weapons & Gear was requested as "an identical text entry feature," the originally single-purpose `CharacterDescription.jsx` was generalized into `CharacterTextField.jsx`, parameterized by label, placeholder, current value, and a save function — used twice rather than duplicated, so any future tweak to the interaction (validation, styling, save mechanics) applies to both fields at once instead of needing to stay manually in sync across two near-identical components.
- **Reveal control, revised to a modal**: originally an inline expand-in-place (collapsed = button; expanded = textarea + counter + Save/Cancel, no modal), reasoned at the time from this project having exactly one modal, reserved for gathering required fields before creating something new. That premise no longer holds — [main-story.md](main-story.md), [story-chapters.md](story-chapters.md), and [party-panel.md](party-panel.md) between them have since added several more modals, including ones that aren't creation flows. Per direct request, the control now opens a modal instead of expanding inline; the modal's *contents* are unchanged (title, textarea, counter, Cancel/Save) — only the container moved from inline-in-panel to `.modal-overlay`/`.modal-panel`, reusing the same pattern as this app's other modals (overlay click = Cancel, panel click does not propagate to the overlay).
- **The toggle button must stay visible while its modal is open, and the modal is sized `wide`**: the first implementation collapsed the toggle button and its modal into one mutually-exclusive return (`if (!expanded) return <button>; return <modal>;`), which hid the button entirely whenever its own modal was open — reported and fixed by making the button and modal siblings, the button always rendered. At the same time, the modal was widened (`.modal-panel.wide`, 600px) and its textarea grown (110px → 320px min-height) per a direct request for more visible text at once.
- **Explicit Save button, not blur/Enter-to-commit.** Every other inline edit in this app (conversation rename, message edit) is single-line and commits on Enter/blur. A 500-character field is genuinely multi-line — Enter needs to insert a newline, and a stray blur (e.g. clicking the character counter) shouldn't silently discard or half-save a long draft. Cancel discards the draft and collapses back without saving.
- **Placement**: both live inside the same character-identity block as the rest, between the avatar frame and the `<hr>` that separates the identity block from the dice roller — Description first, Weapons & Gear directly beneath it, per the request — so the whole "everything about my character" block (name, Role/Level, avatar, description, gear) stays together above that boundary.
- **Feeding both to Claude**: `buildPlayerRoster` in `server/lib/claude.js` already turns `characterNames`/`characterDetails`/`characterDescriptions` into roster text Claude sees. Weapons & Gear was extended the same way — a `characterGear` parameter appends its own short block, listing only players who've saved one. This wasn't explicitly requested for Gear, but the request called it "identical" to Description, whose entire purpose (per the original spec) was informing the DM rather than being inert flavor text — and what a Cyberpunk character is carrying is at least as mechanically relevant to a DM as their appearance. `dm-system-prompt.txt`'s existing instruction was broadened to cover both.
- **Prompt caching**: this text sits inside the same cached system-prompt block as the rest of the roster (see [prompt-caching.md](prompt-caching.md)). Editing either field invalidates that cache the same way editing anything else in the system prompt would — expected, not a regression, and edits are rare (occasional player action) compared to the per-message cache reuse this is optimizing for.
- **Icon-button row, first built with `lucide-react`, later reverted to plain emoji.** The two text-label toggle buttons became a row of square icon-only buttons with a small caption beneath each. First pass used `lucide-react` (`scroll-text`/`briefcase`) specifically because its icons inherit color from CSS via `stroke="currentColor"`, unlike emoji — see [visual-restyle.md](cyberpunk-red/visual-restyle.md)'s handoff. Once the UI handoff mockup arrived showing plain emoji (📝/💼/🌐) for this exact row, asked directly whether to keep color-responsive lucide icons chosen to merely *resemble* the mockup, or match the mockup exactly at the cost of that behavior — chose the exact match. `icon` is now a plain string (the emoji itself) rendered in a `.icon-emoji` span, not a component; `lucide-react` was removed from `client/package.json` since nothing else in the app used it. See [character-map.md](cyberpunk-red/character-map.md) for the third button on the same row (Map) — a separate spec, went through the identical reversal.
- **Caption text can differ from the modal title**: "Weapons & Gear" doesn't fit under a small square button, so `CharacterTextField.jsx` gained a `buttonLabel` prop distinct from `label` (which still titles the modal) — Description's caption and modal title are both "Description" (same text, no divergence needed there); Gear's caption is "Gear" while its modal keeps the full "Weapons & Gear" title.

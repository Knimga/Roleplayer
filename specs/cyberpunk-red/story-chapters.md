# Spec: Story Chapters

## Status
Implemented

## Summary
Extends [Main Story](main-story.md) to handle campaigns whose message history would otherwise grow without bound. A Main Story becomes a **story** — a persistent, independently-named container — made up of an ordered sequence of **chapters**, each an ordinary conversation. Only the latest chapter is ever active; starting a new chapter permanently locks the previous one (read-only, no exceptions, including the admin) and seeds the new one with an admin-reviewed AI summary of what came before, followed automatically by an in-character scene-opening reply — so the DM's working context resets without the players losing continuity.

## Requirements
- [x] "+ New Main Story" is unchanged from the player's perspective: still collects character names, Role, and Level up front
- [x] Creating a Main Story creates both a story (its editable display name defaults to "<CharacterA> & <CharacterB>", same default as today's conversation name) and that story's first chapter, automatically named "Chapter 1"
- [x] The sidebar groups a story's chapters under a section labeled with the story's name; chapters render indented beneath it, in order
- [x] The story's name can be renamed (same inline-rename interaction a conversation already has); a chapter's name can never be edited — it is always "Chapter N"
- [x] Selecting a chapter behaves exactly like selecting any conversation today — same messages, dice roller, avatar, description, and gear functionality
- [x] Only a story's latest chapter accepts new messages, rolls, DM replies, or edits to avatar/description/gear — for anyone, including the admin
- [x] Earlier chapters remain fully viewable (message history, and character data exactly as it was at the time) but are permanently read-only
- [x] Starting a new chapter is admin-only
- [x] Starting a new chapter shows the admin an editable, AI-generated summary of the outgoing chapter's plot for review before anything is created — canceling creates nothing at all
- [x] On approval, a new chapter is created: character name/Role/Level/avatar/description/gear all carry over from the outgoing chapter as the new chapter's starting values, independently editable (and independently lockable, once *this* chapter is superseded) from that point on
- [x] The approved summary becomes the new chapter's first message, followed automatically by a second, in-character DM message that opens the new scene — no extra click required to get the second message
- [x] A story's earlier chapters can never be deleted; deletion is only ever possible for a story's current (latest) chapter, admin-only, same permission as conversation deletion today

## Decisions
- **New `stories` table, not just a field.** Earlier passes considered a lightweight `storyId`/`continuesFrom` pair directly on `conversations`, but a story now has its own independently-editable name that can't live on any single chapter's `name` (chapter names are fixed to "Chapter N"). That requires a real row somewhere to hold it — `stories(id, name, createdAt)`, with `conversations.storyId` as a nullable FK.
- **No `continuesFrom`.** Chapters can never be deleted, reordered, or branched — a story's chapter sequence is always a strict, append-only line. `storyId` plus `createdAt` ordering fully and permanently determines that sequence, so a linked-list pointer would be redundant. Same reasoning means "Chapter N" is a derived display position, not a stored column — nothing can ever happen that would make a stored number drift from actual position, so storing one adds nothing.
- **`isMainStory` stays as-is.** Every chapter row still sets it, even though it's now technically implied by `storyId` being non-null. Collapsing the two would mean touching every one of the many existing `isMainStory` checks across the routes for a redundant-but-harmless cleanup — not worth the churn or risk in this pass.
- **Active-chapter locking is one shared server-side check, not six.** "Only the latest chapter is active" has to gate every mutating route a Main Story conversation currently has: send message, roll, Ask the DM, avatar upload, description save, gear save. A single `assertActiveChapter`-style helper (mirroring how `findModifiableMessage` already centralizes message-locking logic) is applied at all six call sites rather than duplicating the "is there a later chapter in this story?" check six times.
- **Review is a modal, not an editable message.** `findModifiableMessage` makes GM (assistant-role) messages *unconditionally* immune to edits, for anyone, including the admin — that's load-bearing, already-shipped behavior from [message-editing.md](../chat/message-editing.md). Rather than carving a one-time exception into that rule for "this message, until approved," the draft summary simply isn't a message at all until approval — it's ephemeral request/response state in a review modal. Canceling the modal discards it; nothing is ever created. Only the approved, final text is ever inserted as a real message, at which point it's just an ordinary immutable GM message like any other.
- **The recap+intro pairing is its own server-side sequence, not a call to `/:id/respond`.** That endpoint deliberately rejects a second DM reply with no user message in between, to prevent back-to-back DM turns during normal play — and a recap message immediately followed by a scene-intro message is exactly that shape. Chapter creation doesn't route through `/:id/respond` at all; it inserts the recap, calls `generateReply` directly, and inserts the result — so the normal-play guard is simply never in the picture, not bypassed.
- **The recap message is visually distinct from real narration.** It's a DM-authored utility document, not in-fiction narration — rendered with a distinct sender label (e.g. "Story So Far") and no typewriter animation, so it doesn't read as part of the scene the way the scene-intro message right after it should.
- **Character fields are copied forward, not referenced.** Role/Level go from "locked forever" to "locked forever, but re-established via automatic copy at each new chapter" rather than by a player re-entering them — nobody ever types them twice. A useful side effect: reopening an old, locked chapter shows the character exactly as they were *then* — avatar, description, and gear included — since each chapter's values are its own frozen copy, not a shared reference.
- **Sidebar ordering**: a story's position in the (still single, still recency-sorted) sidebar list is driven by its active chapter's `lastMessageAt`, same as any standalone conversation — story sections and ungrouped conversations interleave in one list, sorted the same way as today, rather than being split into separate always-on-top/always-below regions.
- **Backfill for the two existing Main Story conversations.** They predate this feature and have no `storyId`. A one-off script (matching the precedent set by `server/db/backfill-author-username.js`) creates a `stories` row per existing Main Story conversation (name = that conversation's current `name`), points the conversation at it, and renames the conversation itself to "Chapter 1". (At implementation time the local dev database happened to have zero conversations in it, so this ran as a true no-op — the logic was still verified directly against manually-inserted rows before trusting it.)
- **All five Open Questions resolved to their proposed defaults**, confirmed during implementation with no pushback: the active chapter can be deleted (admin-only, reactivating the one before it — only earlier chapters are permanently protected, and deleting a story's last remaining chapter deletes the now-empty story row too); chapters count against the 50-conversation cap with no special-casing; story rename is open to both players; "+ New Chapter" is reachable from the story's menu regardless of which chapter is currently open; the summary textarea has a generous 6000-character soft cap, enforced client-side only (no server-side length rejection — this is an admin-authored document, not a player-facing field).
- **`findModifiableMessage` also needed the chapter-lock check**, not just the six routes originally scoped. The rule "a locked chapter is read-only in every way" doesn't hold if an individual message's edit/delete route only checks for a *later reply within the same conversation* — a chapter can go inactive with its last message still being a **user** message (no trailing GM reply), which would otherwise leave that message editable forever. Fixed by extracting a shared `hasLaterChapter(conversationId, storyId, createdAt)` boolean helper, used by both `assertActiveChapter` (route-level, writes the 403 itself) and `findModifiableMessage` (returns a status/error pair like its other checks).
- **A real bug in the lock check itself, found during testing**: comparing `conversations.createdAt > <this row's own createdAt>` to detect "is there a later chapter" spuriously matched a chapter against *itself*. Postgres stores timestamps at microsecond precision; Drizzle round-trips `createdAt` through a JS `Date` (millisecond precision) once it's fetched and passed back into a query, truncating it — so the real stored value (e.g. `...770997`) compared as `>` a truncated copy of itself (`...770000`) evaluates true. Fixed by having `hasLaterChapter` explicitly exclude the row being checked by id, rather than relying on the timestamp comparison alone to rule out self-matches.
- **The recap-then-intro sequence needed a synthetic "kickoff" message, not just `[recap]`.** The Anthropic API rejects any `messages` array that doesn't end in a `user` turn as unsupported "assistant message prefill" — and both `[recap]` alone (a lone assistant-role message) and, earlier, the chapter-transcript-as-conversation-history approach for `generateChapterSummary` hit this. The summary call was restructured to wrap the whole transcript as a single user message instead of passing it as literal conversation history; the intro call appends a never-persisted synthetic `{ role: "user", sender: "System", content: "Begin the new chapter now..." }` after the recap so the request always ends in a valid user turn.
- **The `/:id/summarize` route needed its own try/catch.** It didn't have one initially; an Anthropic API error inside `generateChapterSummary` (the prefill error above, before the fix) surfaced as an unhandled promise rejection and crashed the whole Node process — Express 4 doesn't catch async route handler rejections automatically. Now caught and returned as a 502, matching how `/:id/respond` already handles its own generation failures.

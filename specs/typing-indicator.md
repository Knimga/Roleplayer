# Spec: Typing Indicator

## Status
Implemented

## Summary
While one player is composing a message, the other player (if they have that conversation open) sees a small animated indicator anchored above the message box reading "[name] is typing...", where `[name]` matches however that player's messages are already attributed (character name in a Story conversation, username otherwise). Purely a presence signal — nothing is persisted, and it's unrelated to the DM's own "awaiting reply" spinner.

## Requirements
- [x] While a player has non-empty text in the message textarea, the *other* player (if viewing the same conversation) sees an indicator, anchored to the message box: a small animated element plus the text "[name] is typing...", left-aligned
- [x] `[name]` is the same name that would appear on that player's sent messages — character name in a Story conversation, username in a regular conversation
- [x] The typing player never sees their own typing indicator
- [x] The indicator disappears shortly after the other player stops typing (goes idle) or sends the message — it doesn't linger indefinitely
- [x] Works for both Story and regular conversations, same as the rest of the chat feature
- [x] Nothing about typing state is persisted — a page reload or reconnect simply shows no indicator until a new typing signal arrives
- [x] The indicator is always visible when active, regardless of scroll position in the message list — it isn't part of the scrollable area

## Decisions
- **Transport: extends the existing per-conversation SSE channel, no new connection.** `ChatView.jsx` already holds one `EventSource` per selected conversation (see [shared-conversation.md](shared-conversation.md)'s envelope, already extended once for the shared "generating" spinner and again for [party-panel.md](party-panel.md)'s `"character-updated"` event). Typing becomes a third example of the same pattern: `{ type: "typing", sender, senderUsername }`, no `message` payload.
- **Client → server signal is a lightweight POST, not a second SSE-like channel.** A browser can't push over `EventSource` (receive-only), so the typing client informs the server via `POST /:id/typing` (no body) whenever it detects active typing; the server resolves the display name via the already-existing `resolveSender` helper (same one message attribution uses) and `publish()`s to that conversation's subscribers — which includes the typing player's own tab, same as every other event this app broadcasts. The client filters out its own pings using `senderUsername` (the real username, sent separately from the display `sender` name) rather than comparing display names, since two different real accounts should never be treated as the same person even if their character names ever collided.
- **Client-side throttling, not per-keystroke.** The textarea's `onChange` fires a typing ping only if at least 2 seconds have passed since the last one (a ref-tracked timestamp, not state — no re-render needed to throttle). This bounds traffic to at most one request every 2s per actively-typing player, regardless of typing speed.
- **Auto-expiry plus clear-on-send, not an explicit "stopped typing" event.** The receiving client shows the indicator for 4 seconds after each ping and re-arms that timer on every new ping — so it naturally disappears ~4s after the other player goes idle, with no dedicated "I stopped" signal to get out of sync. It also clears immediately on receiving any new message in that conversation (the existing `"created"` event), since a message arriving means whatever they were composing is now sent — this avoids the indicator visibly lingering for a few seconds after the message it was for already appeared.
- **No persistence, no database involvement.** Purely an in-memory broadcast through the same `broadcaster.js` used for messages/generating/character-updated — a typing signal that arrives with no one listening (e.g. the other player doesn't have this conversation open) is simply dropped, which is the correct behavior for a presence indicator.
- **Not gated by `isMainStory`/active-chapter checks server-side.** The textarea this reads from is already hidden client-side whenever a chapter is locked (see [story-chapters.md](story-chapters.md)), so the endpoint is unreachable from that state in normal use; adding a redundant server-side lock check for a harmless, unpersisted presence ping isn't worth the extra code, unlike the real data-mutating routes (`PATCH /:id/hp`, message edit/delete, etc.) where that enforcement actually matters.
- **Can coexist with the "awaiting reply" spinner.** These are unrelated signals (a human typing vs. the DM generating) and nothing prevents both from appearing at once if, say, one player asks the DM while the other starts typing their next message — no special mutual-exclusion logic.
- **Retrofit: moved out of `#messages`, anchored above the message box instead.** The first implementation rendered it as the last `<li>` in the scrollable message list — reasonable in isolation, but real play-testing found it effectively invisible: on any conversation long enough to require scrolling, a newly-appearing list item at the bottom doesn't pull the view down (only `messages`/`awaitingReply` changes triggered the scroll-to-bottom effect, not `typingSender`), so the indicator silently sat below the fold. Rather than also wiring it into the scroll-follow effect, it was moved entirely out of the scrollable list — now a sibling of the message form (`.typing-indicator-bar`), always visible regardless of scroll position, immediately above the textarea it's actually about.
- **Retrofit: left-aligned, not center-aligned.** In its original `<li>` placement, the dots ended up left-aligned but the text ended up centered — `#messages li` is a column flex container with no `align-items` set (defaulting to `stretch`), and the app's `#root` sets a global `text-align: center` that the stretched text span inherited while the dots' own inline-flex sizing didn't. The new `.typing-indicator-bar` is a plain `display: flex` *row* (dots and text side by side, `align-items: center`), which puts both on the same horizontal line by construction and needs no explicit `text-align` at all — sidesteps the inheritance bug rather than patching it.

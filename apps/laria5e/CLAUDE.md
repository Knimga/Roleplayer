This project is vibe-coded, not spec-driven — there's no spec.md/plan.md/tasks.md workflow to follow. Read steering/product.md, steering/structure.md, and steering/tech.md regularly; they're the stable, high-level reference for what this app is and how it's built, and should be kept up to date as things change. specs/ is not a workflow folder here — it holds a handful of standalone reference notes on non-obvious gotchas (API quirks, deployment traps, race conditions) inherited from the project this was forked from; read one if it's relevant to what you're touching, but don't expect every feature to have one, and don't create new ones by default.

Dev servers: the user always runs the dev server (`npm run dev` in server/, port 3001; client, port 5173) themselves, in their own VSCode terminal — that instance is the only one to ever develop against. Never start a separate/second instance of either server, even temporarily — past sessions where Claude spun up its own instance led to Claude and the user looking at divergent state, and the user relies on their terminal's own output for visual feedback on status. Before testing or verifying anything, check the user's instance is up (e.g. `curl localhost:3001`) and ask them to start it if it isn't — don't start it yourself. If a separate temporary instance is genuinely needed for some reason, always ask the user first and get their go-ahead before starting it.

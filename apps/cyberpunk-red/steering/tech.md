# Tech

## Stack
- Frontend: React
- Backend: Node.js + Express
- MCP server: Node.js (runs alongside/in-process with the backend)

## Hosting
- Render (public deployment), as a single Web Service — Express serves both the API and the built React frontend (`client/dist`) from the same origin, avoiding CORS/cross-site-cookie complexity entirely. See [render-hosting.md](../specs/render-hosting.md).
- All required env vars are validated at server startup — missing one exits with a clear error rather than degrading silently (e.g. a missing `SESSION_SECRET` would otherwise produce forgeable session cookies instead of an obvious failure)

## AI
- Model: `claude-sonnet-5` via the Anthropic API
- API key stored in a local `.env` file (gitignored) — never committed, even pre-deployment (unlike the temporary repo-committed access codes)
- Real MCP server (`@modelcontextprotocol/sdk`, `mcp/server.js`) exposing `list_lore_files`/`read_lore_file` (over `mcp/lore/*.txt`) and `roll_dice` (NPC/enemy rolls only — players roll their own) — linked to the backend in-process via `InMemoryTransport` (no subprocess, no network hop). `server/lib/claude.js` is the MCP client: it feeds the tool list to the Anthropic API and runs a tool-use loop when Claude calls one. See [lore-file-access.md](../specs/lore-file-access.md) and [npc-dice-roll.md](../specs/npc-dice-roll.md).
- Model instructions injected via system prompt (narration style, game rules, DM behavior, when to call `roll_dice`) — see [dm-system-prompt.md](../specs/dm-system-prompt.md)
- Prompt caching (`cache_control: { type: "ephemeral" }`) on the system prompt, tool definitions, and everything but the newest turn of message history — cuts the cost of resending the whole transcript on every "Ask the DM" call. Pure cost/latency optimization, no effect on output. See [prompt-caching.md](../specs/prompt-caching.md).

## Auth
- Two hardcoded user slots, each with a personal access code and a fixed username
- One user slot is flagged `isAdmin` in config, exposed on the session (`req.user.isAdmin`, and in the `/login`/`/me` responses) for gating admin-only actions — first use is conversation deletion
- Codes/usernames/admin flags and the session-signing secret are sourced from environment variables (`USER_A_CODE`/`USER_A_USERNAME`/`USER_A_ADMIN`, `USER_B_*`, `SESSION_SECRET`) — no longer hardcoded in the repo. See `server/.env.example`.
- Session persists across page refresh via a signed session cookie
- No user registration or account system at MVP

## Conversations
- Sidebar-listed conversations, sorted by most recent activity — no conversation selected on page load; sending a message with none selected creates one (named with today's date). See [conversation-management.md](../specs/conversation-management.md).
- A pinned/visually-distinct "main" RP conversation is deferred (not built) — see that spec's Decisions
- Cap of 50 conversations; hitting it blocks creating a new one until an old one is deleted (admin-only)
- Shared conversation state: both users see the same message history within a conversation; the *set* of conversations is shared, but which one is selected is local per-browser-session state, not synced live between users
- Real-time message syncing via Server-Sent Events (SSE): server pushes new messages to clients; clients send new messages via regular HTTP POST
- Claude never responds automatically — either user must explicitly ask for the DM's turn, and that request is rejected if the last message is already from Claude (no back-to-back DM turns). A second "Ask the DM" while one is already generating is also rejected — found via real play-testing (two users clicking close together produced two DM replies in a row) — via an in-memory `pendingReplies` Set of conversation ids, checked-and-added synchronously before any `await` so there's no race window. The pending state is also broadcast over SSE (`{ type: "generating" }` / `{ type: "failed" }`, no `message` payload) so *both* players see the spinner and have their "Ask the DM" button disabled, not just whoever clicked it.
- A right-side dice-roller panel (mirroring the sidebar) lets a player build and submit a roll, which posts as an ordinary message via `POST /:id/roll` — same dice/crit math as the NPC `roll_dice` MCP tool (shared in `mcp/dice.js`), same message-insertion path as typing (shared `resolveSender`/`insertUserMessage` helpers). See [player-dice-roller.md](../specs/player-dice-roller.md).
- The right panel (`RightPanel.jsx`) is a column of stacked sections separated by `<hr>`s, per [product.md](product.md)'s UI Layout convention. When a Main Story conversation is selected, the current user's character name renders as a centered header at the top, above an `<hr>`, above the dice roller; hidden entirely for non-Main-Story conversations (derived from the already-computed `characterNames[username]`, same value `ChatView` uses).
- Main Story creation also locks in a Role (one of the ten fixed Cyberpunk Red roles) and a Level (1-20) per player, stored in a separate `character_details` jsonb column (`{ username: { role, level } }`) alongside `character_names` — same locked-forever lifecycle, kept in its own column so name-only read paths are untouched. Displayed as "Level {level} {role}" in small gray italics under the character name header. See [character-role-level.md](../specs/character-role-level.md).
- Each Main Story player can also upload a character avatar, shown in a fixed 250×300 frame below the name-header-and-Role/Level grouping (separated by its own `<hr>`) — unlike name/role/level, this is optional and replaceable at any time, not locked at creation. Stored as a base64 data URL directly in a mutable `avatar_images` jsonb column (`{ username: dataUrl }`) rather than on disk, since Render's Web Service filesystem doesn't survive a redeploy and there's no object storage configured; `express.json()`'s body limit is raised to `5mb` to fit one (max 3MB per image, enforced both client- and server-side). The image's width is scaled to fill the frame exactly and vertically centered, with overflow clipped. See [character-avatar.md](../specs/character-avatar.md).
- Users can edit or delete their own messages; the admin can edit/delete either player's. GM messages are never editable/deletable by anyone, and a message locks for everyone (including the admin) once any GM reply exists later in the conversation — enforced server-side in a shared `findModifiableMessage` check on every request, not trusted from client state. SSE `publish()` now sends an envelope `{ type: "created" | "updated" | "deleted", message }` on every call site (including the two pre-existing ones); the client updates-in-place or removes a message rather than always appending. `messages.author_username` (real username, independent of the possibly-character-name `sender`) and `messages.edited` back this — pre-existing messages were backfilled via `server/db/backfill-author-username.js` (direct for regular conversations, reverse-lookup through `characterNames` for Main Story ones). See [message-editing.md](../specs/message-editing.md).
- Each Main Story player can also write a physical description and a Weapons & Gear list for their character (≤500 chars each), stored in mutable `character_descriptions`/`character_gear` jsonb columns (`{ username: text }`, same lifecycle as `avatar_images` — editable any time, not locked). Both use the same reusable `CharacterTextField.jsx` component (label/placeholder/value/save-function as props) — Weapons & Gear was added as "an identical text entry feature" directly beneath Description, which is why they share one component instead of two near-copies. Hidden by default behind a small toggle button in the right panel (between the avatar frame and the divider before the dice roller, Description above Weapons & Gear); expanding shows a textarea with a live character counter and explicit Cancel/Save buttons rather than committing on blur/Enter, since Enter needs to insert a newline in a field this long. Both are actually fed to Claude, not just stored: `buildPlayerRoster` in `server/lib/claude.js` appends a block per field (via a shared `formatFieldBlock` helper) to the system prompt for players who have one saved, and `dm-system-prompt.txt` tells Claude to let physical description inform NPC reactions and let listed gear inform combat/searches/NPC reactions to what's visibly carried. See [character-description.md](../specs/character-description.md).
- A Main Story (UI-facing term is now just "Story" — `NewMainStoryModal.jsx`/`createMainStory`/`#new-main-story`/`.main-story-icon` were renamed to `NewStoryModal.jsx`/`createStory`/`#new-story`/`.story-icon` in the frontend; `isMainStory`/`is_main_story`/the `/main-story` route were deliberately left as-is, since nothing but the developer ever sees those — see [main-story.md](../specs/main-story.md)'s Decisions) is really a **story** — a `stories` row (`id`, `name`) with its own independently-editable name — made up of an ordered, append-only sequence of **chapters**, each an ordinary `conversations` row with `storyId` set. Only the latest chapter of a story is ever mutable; a shared `hasLaterChapter`/`assertActiveChapter` check (plus `findModifiableMessage` and `DELETE /:id`) locks everything else about an earlier chapter — messages, rolls, DM replies, avatar/description/gear, even individual message edits — permanently read-only for everyone, including the admin, once a newer chapter exists. "Chapter N" is never stored, just derived from `ORDER BY createdAt` within a `storyId`, since chapters can't be deleted, reordered, or branched. Starting a new chapter (admin-only, from the story's sidebar ellipsis menu) is a two-step, review-before-create flow: `POST /:id/summarize` generates a structured AI summary of the outgoing chapter for the admin to edit in a modal (nothing persisted yet — this sidesteps needing an exception to GM messages' unconditional edit-immunity), then `POST /:id/new-chapter` creates the chapter with copied character fields (frozen forward, not referenced — reopening an old chapter shows the character exactly as they were then) and inserts the approved recap (`sender: "Story So Far"`, styled distinctly, no typewriter) followed automatically by a real scene-opening DM reply, generated directly rather than through `/:id/respond` (whose back-to-back-DM-turn guard would otherwise reject that exact sequence). Two Anthropic-API gotchas surfaced building this: a `messages` array must end in a `user` turn (a chapter transcript ending in the DM's last reply, or a bare `[recap]`, both get rejected as unsupported "assistant prefill" — fixed by wrapping the transcript as one user message for the summary call, and appending a synthetic never-persisted kickoff message for the intro call) — and a Drizzle round-trip of `createdAt` through a JS `Date` truncates Postgres's microsecond precision, so a naive `createdAt > thisRow.createdAt` comparison can spuriously match a row against itself unless it's also excluded by id. See [story-chapters.md](../specs/story-chapters.md).

- Every `<h2>` in the app (modal titles, `LoginScreen`'s heading) is styled by a global `h1, h2 { font-family: var(--heading); ... }` rule in `index.css`. `--heading` was still the original template's plain system-font stack, never updated when the app's body font became `'Chakra Petch'` — so every `<h2>` rendered in a visibly different font from the rest of the app. Fixed by setting `--heading: 'Chakra Petch', sans-serif;` to match `body`'s font-family; a one-line, app-wide fix rather than patching each modal's own CSS.

## Persistence
- Postgres (Render managed Postgres in prod; Docker container locally for dev)
- Accessed via Drizzle ORM (typed queries + migrations)
- Stores: conversations, messages, user/session state
- Lore `.txt` files remain flat files in the repo (read by the MCP server), not in the database

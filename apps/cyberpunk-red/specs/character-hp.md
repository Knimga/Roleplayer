# Spec: Character HP

## Status
Implemented

## Summary
Extends [Main Story](../conversations/main-story.md)'s right panel with an HP & Wound State tracker: a new `hr`-separated section directly beneath the avatar frame, above Description/Weapons & Gear. Current and max HP are player-editable, persistent values (mutable anytime, same lifecycle as avatar/description/gear — optional at creation, not locked). Wound State is derived from them on the fly and never stored. The DM is told a character's Wound State during LLM calls, never the raw HP numbers — this makes HP the first piece of right-panel character data that is visible to players but deliberately withheld from the LLM (every other field — name, role, level, description, gear — is sent in full; see Decisions).

## Requirements
- [x] A new `hr`-separated section appears directly beneath the avatar frame, before the Description/Weapons & Gear fields
- [x] HP bar: thin horizontal bar, rounded corners, width equal to the avatar frame's width (250px). A muted background track spans the full width; a fill portion scales proportionally to current/max HP (e.g. 60% width at 60% HP)
- [x] Fill color: green when Healthy, pale green-yellow when Lightly Wounded, orange when Seriously Wounded, red when Mortally Wounded
- [x] HP numbers ("47/47" format) render centered beneath the bar; current and max are each independently editable
- [x] After editing, the numbers' text color matches the bar's current color
- [x] Wound State renders as small text beneath the HP numbers: "Healthy", "Lightly Wounded", "Seriously Wounded", or "Mortally Wounded" — light green for Healthy, pale green-yellow for Lightly Wounded, light orange for Seriously Wounded, pink for Mortally Wounded
- [x] Wound State thresholds: Healthy = current equals max; Lightly Wounded = current is more than half of max (and less than max); Seriously Wounded = current is at or below half of max but at least 1; Mortally Wounded = current is less than 1
- [x] HP is persistent, per-character, per-conversation data — saved to the backend like avatar/description/gear, not just held in frontend state
- [x] When a new Story is created, both players' HP is initialized to 0/0 (not left blank/unset)
- [x] At 0/0, the bar shows no colored fill (empty/neutral track) and Wound State renders blank — 0/0 is a "not yet configured" placeholder, not a real Mortally-Wounded reading
- [x] The section is absent for non-Story conversations, same as the rest of the character-identity block
- [x] The section is locked (read-only) once its chapter is no longer the active one, same as avatar/description/gear
- [x] During "Ask the DM" calls, the DM's system prompt includes each player's current Wound State (when set); it never includes raw HP numbers
- [x] The other player's Wound State (not their raw HP) is visible in the Party panel, colored the same way as the current user's own Wound State, and updates immediately (no manual refresh) when their HP changes such that their Wound State changes — see [party-panel.md](party-panel.md)

## Decisions
- **Storage**: a new `character_hp` jsonb column on `conversations`, shaped `{ "<username>": { "current": <int>, "max": <int> } }` — same per-username map convention and mutable-anytime lifecycle as `avatar_images`/`character_descriptions`/`character_gear` (see [character-avatar.md](character-avatar.md)). Unlike those fields, a value is always present for both players from the moment a Story is created (see Initial value, below) — there is no "missing key" state to handle.
- **Initial value & the 0/0 special case**: `POST /main-story` seeds `character_hp` with `{ current: 0, max: 0 }` for both players at creation time, alongside `characterNames`/`characterDetails`. `max === 0` is treated as the sentinel "not yet configured" state everywhere HP is read: `computeWoundState` returns blank/`null` instead of applying the four thresholds (avoiding both a divide-by-zero and the misleading `current === max` → "Healthy" false positive at 0/0), the bar renders its empty track with no colored fill, and the numbers render in a neutral/muted color rather than green/orange/red. Because a real value always exists from creation, there's no separate "unset" UI mode — Current and Max are independently click-to-edit from the very first render (see Editing interaction), defaulting to "0/0" text.
- **Editing interaction**: clicking the current number or the max number independently turns just that number into a small inline `<input type="number">` — Enter saves, Escape cancels, blur saves — mirroring the sidebar's existing rename-input interaction (click → inline input → Enter/blur to commit) rather than requiring an expand/Save/Cancel round trip for a quick mid-scene HP update.
- **Validation**: server-side and authoritative, applied to every `PATCH /:id/hp` call (the 0/0 creation-time seed bypasses this, since it's written directly by the creation route, not through this endpoint). Max must be a positive integer (≥1) — so a player's first real edit is naturally to set Max HP to something meaningful. Current must be an integer and may be zero or negative (Cyberpunk Red's mortal/death-save range extends below 0); current may not exceed max. Re-checked on the request regardless of client-side gating, per this project's established server-side-enforcement pattern.
- **Endpoint shape**: `PATCH /:id/hp` accepts a partial body — either or both of `{ current, max }` — merges onto the username's existing stored value, validates the merged result, and persists it. This lets the frontend send just the one number the player edited, without needing separate endpoints or a combined first-time form.
- **Who can edit**: self-only, same as description/gear — a player edits their own HP; there's no admin override and no editing the other player's HP from the Party panel/modal (that remains strictly read-only, per [party-panel.md](party-panel.md)).
- **Showing the other party member's Wound State, reversing an earlier "explicitly out of scope" call**: this spec originally deferred both "show the other player's Wound State in Party" and "live SSE push of an HP change" — per direct follow-up request, both are now implemented; see [party-panel.md](party-panel.md) for the Party-side Requirements/Decisions and the SSE mechanism. What's still true, unchanged: the other player's *raw* HP numbers are still never surfaced anywhere in the UI (Party only ever computes and shows the derived Wound State), and HP is still never editable from the Party panel.
- **Wound State computation: duplicated across client/server, but shared within the client.** The threshold logic (`current`/`max` → one of the four states, plus the `max === 0` blank case) still exists once server-side (`claude.js`, for the DM roster line) as an intentionally independent copy — this project has no shared client/server code path, and duplicating a small function is more consistent with this codebase's patterns than building one. Client-side, though, it moved from living only in `HpTracker.jsx` to a small shared `client/src/woundState.js` module once [party-panel.md](party-panel.md) needed the exact same computation for the *other* player's HP — two call sites in the same JS runtime is a real "must stay in sync" risk that a same-language `import` trivially solves, unlike the client/server split.
- **LLM roster wiring**: `buildPlayerRoster` in `server/lib/claude.js` gains a new `characterWoundStates` parameter (a `{ username: "<Wound State>" }` map computed by the route handler from the stored `character_hp` before calling `generateReply`), appended via the same `formatFieldBlock` helper already used for Descriptions/Weapons & Gear — which already skips any player with no (falsy) value, so the still-at-creation-defaults 0/0 case naturally adds no Wound State line rather than sending a misleading one. Only the computed label reaches the model; the numeric `current`/`max` values are never included in any Claude request.
- **First right-panel field withheld from the LLM, by design**: every other piece of character-identity data on the right panel — name, role, level, description, weapons & gear — is sent to the DM in full (see `buildPlayerRoster` in `server/lib/claude.js`). Raw HP (`current`/`max`) breaks that pattern deliberately: the DM only ever receives the derived Wound State string, never the numbers themselves. This is an intentional design choice (the user's framing: "the DM only needs to know Wound State, not exact HP"), not an oversight or a gap to later "fix" by also sending raw HP — any future work on this feature should preserve the omission.
- **New-chapter carryover**: like avatar/description/gear, `character_hp` carries over as the new chapter's starting value when an admin starts a new chapter (see [story-chapters.md](../conversations/story-chapters.md)) — whatever the outgoing chapter's values are (real HP, or still the 0/0 default if the player never set it) becomes the new chapter's starting value, then becomes independently editable/lockable from that point on. This applies alongside the other character fields already carried over (name, role/level, avatar, description, gear) — HP is one more field in that same copy, not a separate mechanism.
- **Retrofit: "HP" label added by [character-sp.md](character-sp.md)**: the numbers row originally read bare "47/47". Once an SP tracker was added directly beneath it, the two needed to be distinguishable, so the numbers row now reads "HP 47/47" — a small UI change made as part of the SP work, not a re-scoping of this feature. The underlying `HpTracker.jsx` was also refactored at that point to share its bar/number/editing logic with the new SP tracker via `NumberBarTracker.jsx`, with no behavioral change to HP itself.
- **Retrofit: Lightly Wounded gets its own color, no longer sharing green with Healthy.** A new `hp-yellow-green` color tier was added to `woundState.js`'s `COLOR_CLASS` map and `App.css` (bar fill `#9acd32`, numbers `#9acd32`, Wound State label `#d9e87a` — a pale green-yellow, following the same saturated-for-bar/numbers vs. pale-for-label pattern already used for the other three states) — Healthy keeps the original green (`#4caf50`/`#90ee90`) unchanged. Since [party-panel.md](party-panel.md) now also reads this same color via `woundStateColorClass`, the Party row's Wound State text picks up the distinction automatically, with no changes needed there.

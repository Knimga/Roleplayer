# Spec: Party Panel

## Status
Implemented

## Summary
Extends [Main Story](../conversations/main-story.md)'s right panel with a read-only "Party" section: a single row showing the other player's character (name, level, role), sourced from data already on the selected conversation. Clicking the row opens a modal with a fuller view — avatar, description, and gear — of that character.

## Requirements
- [x] A new `hr`-separated section appears in the right panel, header "Party", styled to match the Dice Roller header (centered, bold)
- [x] The section shows a single row for the other player's character, format `[CHARACTER NAME ALL CAPS] - Level [level] [role]`, left-aligned, character name bold
- [x] The section (and row) is absent for non-Story conversations, same gating as the rest of the character-identity block
- [x] The row's layout: character name on its own line, level/role on a second line beneath it in smaller text — both left-aligned — and the other player's current Wound State right-aligned, vertically centered against the two-line name/level/role block
- [x] The Wound State text is color-coded the same way the current user's own Wound State is (light green / light orange / pink for Healthy-or-Lightly-Wounded / Seriously Wounded / Mortally Wounded); nothing renders there if the other player's HP is still at its 0/0 default
- [x] When the other player's HP change results in a different Wound State, that update appears in this row immediately, without the viewing player needing to switch conversations or otherwise trigger a refetch
- [ ] The row's third line (see [ready-status-placeholder.md](../ui/ready-status-placeholder.md)) shows the other player's real "ready for DM" status, live — see [ready-for-dm.md](../chat/ready-for-dm.md) for the feature this now reflects
- [x] Hovering the row shows a highlight and a pointer cursor, signaling it's clickable
- [x] Clicking the row opens a modal showing: the other character's name/level/role (same styling as the current user's own header, single line, top-left), their avatar at the same 250×300 dimensions as the right panel's avatar frame, and their Description and Weapons & Gear text (each under a small header), avatar on the left and text fields to its right
- [x] The modal has a landscape aspect ratio
- [x] The modal closes via a single "Okay" button or by clicking outside it (same convention as other modals in this app)

## Decisions
- **Data source**: no new fetch — `characterNames`, `characterDetails`, `avatarImages`, `characterDescriptions`, `characterGear`, and (as of this Wound State addition) `characterHp` are already present on every conversation returned by `GET /api/conversations`; the "other" username is derived client-side as the one key in `characterNames` that isn't the current session's own username (always exactly one, since every conversation has exactly two players). The wire payload already includes the other player's *raw* HP numbers (the list endpoint returns the whole `character_hp` map, both usernames, for anyone who can see the conversation) — nothing new had to be added server-side for that; only Wound State's own display was new. `Party.jsx` computes the Wound State client-side from that raw data and never renders the numbers themselves.
- **Wound State reuses `character-hp.md`'s color scheme, via a shared function**: `computeWoundState`/its color-class mapping moved out of `HpTracker.jsx` into `client/src/woundState.js` (`computeWoundState(current, max)`, `woundStateColorClass(woundState)`), imported by both `HpTracker.jsx` (the current user's own tracker) and `Party.jsx` (the other player's, read-only). See [character-hp.md](character-hp.md)'s updated Decision on this — client/server duplication is kept (different runtimes), but the two client-side call sites now share one implementation.
- **Live update reuses the existing per-conversation SSE channel — no new subscription.** `ChatView.jsx` already holds an open `EventSource` for the selected conversation (for chat messages) and already calls `onActivity?.()` — which `App.jsx` wires to `refreshConversations` — after handling other event types. `PATCH /:id/hp` now also calls `publish(conversationId, { type: "character-updated" })` on a successful save; `ChatView.jsx`'s event handler treats that type as an early-return case (like the existing `"generating"`/`"failed"` handling) that calls `onActivity?.()` and touches no message state. The result: any HP save, by either player, triggers `refreshConversations()` on every client with that conversation open, and Party's Wound State re-renders with the fresh data — no polling, no second connection.
- **Reverses two "explicitly out of scope" notes from `character-hp.md`'s original plan**: that spec's first pass deliberately deferred both "show the other player's Wound State" and "live SSE push of an HP change." Both are what this addition implements — see [character-hp.md](character-hp.md)'s Decisions for the reversal note.
- **Row layout restructured for the new right-aligned Wound State**: `.party-member` changes from a single centered line of text to a flex row (`justify-content: space-between`) — a left column (`.party-member-info`, flex column: name, then a smaller `.party-member-level-role` line) and, when set, a right-aligned Wound State span reusing the existing `.wound-state`/`.wound-state.hp-green|hp-orange|hp-red` classes `character-hp.md` already defined (same color values, same class names — not a second copy of that palette). The whole row, including both new lines, stays within the existing clickable/hoverable `.party-member` element — clicking anywhere in it (name, level/role, or the Wound State text) still opens the modal, unchanged from before.
- **Read-only**: this panel and its modal never write anything — no edit affordance on the other player's character data, consistent with the existing self-directed-only pattern for avatar/description/gear (see [character-avatar.md](character-avatar.md)).
- **Styling reuse over duplication**: the modal's name/level/role header reuses the same visual treatment (uppercase + cyan glow for the name, small italic gray for level/role) as `#character-name-header`/`#character-role-level` in the main identity block, but laid out inline/left-aligned instead of stacked/centered, since the modal calls for a single line. The avatar frame reuses the existing `.avatar-frame` class for identical sizing, with hover/click affordances suppressed (the modal's avatar is display-only, not clickable-to-upload like the user's own).
- **CSS scoping bug found during implementation**: the Dice Roller header rule was originally `#dice-roller strong, #party strong { display: block; ... }`. Once the Party row's character name was also wrapped in a `<strong>` (per a follow-up request to bold it), this rule matched that `<strong>` too and forced it onto its own line, breaking the single-row layout. Fixed by giving the section header a dedicated `.section-header` class and scoping the block/centered rule to `#party .section-header` instead of `#party strong`.
- **Modal dimensions**: fixed at 640px wide, height driven by content (~440px with the 300px-tall avatar plus header/fields) — landscape by construction rather than a hardcoded aspect ratio, matching how other modals in this app size themselves to content rather than the viewport.
- **No spec existed before implementation**: this feature was implemented directly, then this spec was written retroactively at the user's request, per `CLAUDE.md`'s spec-driven-development rule. Requirements/Decisions above reflect what was actually built and verified, not a forward-looking plan.

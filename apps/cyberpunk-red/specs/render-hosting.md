# Spec: Render Hosting

## Status
Implemented (code-side; provisioning the actual Render service/Postgres/env vars is a manual dashboard task — see tasks.md)

## Summary
Prepare the app for public deployment on Render as a **single Web Service** — Express serves both the API and the built React frontend from the same origin, avoiding CORS and cross-site-cookie complexity entirely. Secrets currently committed to the repo (access codes, session secret) move to Render environment variables. A Render-managed Postgres add-on replaces the local Docker database.

## Requirements
- [x] Express serves the built client (`client/dist`) as static files, with an `index.html` fallback for any non-API route, from the same origin as the API
- [x] Client API calls (`client/src/api/auth.js`, `client/src/api/conversations.js`) use relative paths instead of the hardcoded `http://localhost:3001` base — including the SSE `EventSource` connection
- [x] Access codes, usernames, admin flags, and the session-signing secret move from `server/config/users.js`'s hardcoded values to Render environment variables
- [x] `NODE_ENV=production` is explicitly set on Render (not assumed) so the session cookie's `secure` flag actually activates
- [x] Postgres migrations run against the Render production database before the app is usable
- [x] `server/.env.example` is added, documenting every env var the deployed app needs

## Decisions
- **Single Web Service**, not a separate API + Static Site pair. Same-origin means the existing CORS middleware (`server/index.js`) doesn't get exercised in production. Correction made during implementation: the local dev Vite proxy (below) means the browser never makes a cross-origin request in dev either anymore — it only ever talks to port 5173, and Vite forwards `/api/*` to Express server-side. So the CORS middleware is effectively unused in both environments now, not "still needed for local dev" as originally assumed here. Left in place anyway (harmless, and a safety net if the deployment topology ever changes back to two services) rather than removed as unrequested cleanup.
- **Client `API_BASE` becomes relative** (`/api/...`) rather than a build-time-injected env var — works because production always serves frontend and API from the same origin. Locally, a Vite dev-server proxy (`server.proxy` in `client/vite.config.js`) forwards `/api/*` from port 5173 to Express on port 3001, so the same relative paths resolve correctly in both environments with zero env-conditional branching in the client code.
- **Startup env var validation**: discovered during implementation that a missing `SESSION_SECRET` doesn't fail loudly by default — `cookie-parser(undefined)` silently accepts it instead of throwing, which would degrade into forgeable session cookies rather than a visible error. `server/index.js` now checks all required env vars at startup and exits with a clear message if any are missing, rather than relying on downstream libraries to fail safely (they don't, necessarily).
- **Secrets migration**: `server/config/users.js`'s hardcoded codes/usernames/admin flags and `SESSION_SECRET` move to env vars — individual flat vars (`USER_A_CODE`, `USER_A_USERNAME`, `USER_A_ADMIN`, `USER_B_CODE`, `USER_B_USERNAME`, `USER_B_ADMIN`, `SESSION_SECRET`), not a single JSON blob. Render's env var UI is a flat list of plain text fields with no syntax highlighting or validation — a malformed JSON blob would crash the app at startup on a typo that's hard to spot, whereas flat vars are trivial to read/edit individually and there's a fixed, never-growing set of exactly two users.
- **Local dev needs the same env vars**: once `server/config/users.js` reads from `process.env` instead of hardcoding values, local `server/.env` must also define all seven vars above (it currently only has `DATABASE_URL`/`ANTHROPIC_API_KEY`) — a one-time local setup step, not a recurring one. Everything else about local dev (`npm run dev`, Docker Compose for Postgres) is unaffected.
- **Migrations run manually** — no shell access on Render's free tier, so instead `server/.env`'s `DATABASE_URL` is temporarily pointed at Render's Postgres **External Database URL**, `npm run db:migrate` is run locally, then `.env` is switched back to the local Docker URL. Simplest option given there's no CI/CD pipeline for this project yet. Revisit only if this becomes a real pain point across repeated deploys.
- **`db:migrate` runs a custom script (`server/db/migrate.mjs`), not the `drizzle-kit migrate` CLI directly.** Discovered the CLI is unreliable against Render's External Database URL: without an SSL option it fails instantly with no error printed (just stops after "Using 'pg' driver for database querying"); even after adding `ssl: { rejectUnauthorized: false }` to `drizzle.config.js`'s `dbCredentials`, it still exited 1 with no message. Calling `drizzle-orm/node-postgres/migrator`'s `migrate()` directly — same SSL logic, applied only when `DATABASE_URL` isn't `localhost` — worked cleanly and surfaces real errors via a normal try/catch. `drizzle.config.js` still needs the same conditional `ssl` option for `db:generate`/introspection commands, which do go through the CLI.
- **`server/db/seed.js` is not part of the deploy process.** It seeds a legacy `isMain: true` "Main" conversation from an earlier single-conversation architecture; nothing in the current sidebar/dynamic-conversation design reads `isMain` anymore, so running it in production would just create an orphan conversation nobody asked for. Left as-is in the repo (unused, not deleted) unless a cleanup pass wants to remove it later.
